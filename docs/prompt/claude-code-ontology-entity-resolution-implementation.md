# Claude Code 实施提示词：本体驱动的 PostgreSQL 主数据实体解析

> 使用方式：在 `sap-nexus-agent` 仓库根目录启动 Claude Code，将本文件作为任务输入。本文授权实施仓库内的代码、配置、测试与文档改动；不授权连接生产 SAP/HANA、获取真实主数据、调用付费模型、修改生产资源或向远程仓库推送。

## 你的任务

在现有 SAP Nexus Agent 中，实现一套**本体驱动、数据源可替换的主数据实体解析层**。

用户通常只知道物料、客户、供应商的不完整描述，不知道编码。系统应从描述搜索真实候选，必要时询问用户，获得明确的对象引用后，再把真实编码绑定到既有业务能力的参数。

第一版使用本地 PostgreSQL 保存经授权导入的 SAP 主数据检索投影，不修改 SAP，不直接连接 HANA。后续允许通过新的数据源 Adapter 接入 HANA，但本次不实现 HANA 连接器。

**请实施可运行的端到端闭环，不要只输出设计文档、接口空壳、Mock 演示或计划。** 但必须诚实区分：合成数据验证、真实 PostgreSQL 验证、FakeGateway 业务执行，以及尚未完成的真实 SAP 验证。

默认中文解释与文档；代码、注释、标识符和文件名使用英文。默认单 Agent，不启动 subagent。

## 1. 场景与已确认架构决策

### 1.1 典型交互

示例均为合成数据，不代表真实 SAP 主数据。

用户：

> 查一下蓝色耐高温密封圈在 1000 工厂的库存。

系统：

1. 识别库存查询目标和待解析物料描述，不编造物料编码。
2. 根据对象语义与解析规则选择 Material 搜索能力。
3. 从 PG 检索当前 principal 可访问的物料实例。
4. 找到多个候选时，显示正式描述、编码和实际存在的区分属性。
5. 用户回答“第二个”或“直径 20 的那个”。
6. 在原始候选集中确认唯一实体，记录选择证据。
7. 将真实编码绑定到库存能力的 `material` 参数，保留 `plant=1000`。
8. 通过原有服务端治理链继续查询；演示环境通过 FakeGateway 验证恢复执行，不伪装成真实 SAP 查询。

客户和供应商复用同一解析与选择机制，最终分别绑定当前能力实际需要的 `customer`、`customerNumber`、`vendor` 等参数。

### 1.2 不可改变的决策

- PG 是 **SAP 主数据的只读检索投影**，不是第二套主数据权威源。
- 本体声明逻辑对象、身份、属性、解析策略及语义绑定，不存储数据库凭据，不向 Harness 暴露物理表或自由 SQL。
- 数据源 Adapter 负责物理映射、固定参数化查询、分页、候选召回和数据来源信息。
- 用户描述 `EntityMention`、数据库实体 `Entity`、搜索候选 `EntityCandidate`、已解析引用 `ResolvedEntityRef` 必须分开建模。
- 模型负责理解用户表达；真实编码只能来自受治理的数据访问和验证。
- 模糊匹配的单个候选不自动等于唯一正确对象。
- 不引入 Open Ontologies、图数据库、向量数据库或通用 Text-to-SQL 作为本次前置依赖。
- 不把现有全部业务逻辑改成本体规则，不重写 Harness、Planner 或 Gateway 架构。
- PostgreSQL 到 HANA 的可迁移性来自稳定逻辑契约与 Adapter 隔离，不承诺 SQL、索引、相似度阈值和权限策略原样迁移。

### 1.3 范围

本次应完成：

- 物料、客户、供应商三类对象的最小搜索、消歧、编码绑定契约。
- Material 先完成完整纵向闭环，再用同一机制接通 Customer、Supplier，不复制三套编排逻辑。
- PG schema、迁移、合成数据、快照导入、真实 PG 搜索 Adapter。
- 服务端候选状态、DSH Chat 候选选择、自然语言选择和原目标恢复。
- 声明式参数绑定、权限/范围检查、语义版本与数据版本管理。
- 自动化测试、回归样本、运行说明与回滚方式。

不在本次范围：

- SAP 侧自开发、真实 SAP 主数据提取器、生产同步/CDC。
- HANA Adapter 的真实实现或生产身份系统改造。
- 全企业主数据治理平台、自由 SQL、通用动态数据接入平台。
- 基于一次用户确认永久学习公共别名。
- 新增 SAP 写入场景。既有写入流程只允许必要的安全回归，不得改变审批要求。

## 3. 模块边界与数据源接口

### 3.1 稳定接口

定义窄的主数据 Provider/Adapter 契约，至少覆盖：

- `search(request, trusted_scope)`：搜索可见实体候选。
- `get_by_key(entity_key, trusted_scope)`：验证确定编码及其当前状态。
- 数据快照/覆盖范围信息查询，或通过上述响应携带等价信息。

接口名可以遵循仓库约定，但上层不得依赖 PG 表结构或 PG SQL。

搜索请求应包含：对象类型、描述/编码、语言、允许的业务过滤条件、分页/limit。

可信身份、系统/client、允许组织范围由服务端注入，不能由模型或请求体自行授予。

统一候选响应应包含：

- 稳定实体键：来源系统、client、对象类型、规范编码。
- 正式名称/描述与实际可得的区分属性。
- 匹配方式及理由，例如 exact-code、exact-label、approved-alias、substring、trigram。
- 数据版本/快照、来源提取时间与加载时间。
- 分页、截断、覆盖范围及检索是否完整的信息。
- 可选排序分数；分数仅属于具体 Provider，不作为跨数据库统一正确性概率。

显式区分：无匹配、需要缩小范围、数据源不可用、权限不足、快照过期、覆盖不完整。异常不能返回成空候选冒充“没有匹配”。

### 3.2 接入现有 Gateway

搜索应作为注册的 READ 能力，通过现有安全边界访问，不能让 DSH、浏览器或任意 Python 子进程直接获得 PG 凭据。

优先复用现有常驻 Gateway/后端的连接池与治理模式，实现窄的主数据搜索 TechnicalAdapter；具体语言和注册位置以当前代码最小改动为准。

如选择已有 REST_JSON 接受本地受控服务，必须先验证现有 Adapter 确实支持所需请求/响应、认证、审计与网络限制；不得假定兼容，也不得无理由新增微服务。

不提供任意 SQL、任意表名、任意数据库地址或自由查询表达式入口。

如新增 executor/binding 类型，必须同步更新所有实际消费的 schema、模型、loader、validator、dispatcher、代码生成与测试。不要假装只加 YAML 就已接通。

## 4. 本体与映射契约

建议增加独立实体解析目录，如 `ontology/entity-resolution.yaml`，以及服务端专用物理绑定目录；名称以仓库惯例为准。

### 4.1 逻辑对象规则

至少声明：

- `objectTypeId`。
- 标识符 semanticType。
- 逻辑标识字段与显示名称字段。
- 允许搜索的描述、别名和区分属性。
- 受支持的组织过滤与语言维度。
- 对应注册搜索能力。
- 精确/模糊匹配的确认策略。
- 候选展示字段与实际输出契约。

Material、Customer、Supplier 的参数绑定应通过当前 capability input 的 semanticType 与显式映射实现，不能只按字符串包含 material/customer/vendor 判断。

复核 Customer 是否已存在于当前对象目录；缺少则补齐，并与当前实际使用的 `CustomerNumber` 等语义类型对齐。

### 4.2 物理映射

物理映射描述逻辑字段到白名单关系/视图/列的对应关系，由服务端 Adapter 消费。数据库类型、SQL 方言、查询模板、索引实现留在 Provider。

映射文件属于可信配置，不允许用户或 LLM 修改其表名/列名。连接凭据不进入本体文件。

两种可接受实现：

1. 通过规范化数据库视图暴露稳定逻辑字段，绑定到固定查询。
2. 通过经过 schema 校验和白名单约束的字段映射生成有限查询。

选择更简单、可审计的一种，不建设通用 ORM/本体查询编译器。

### 4.3 发布与校验

- 规则引用的对象类型、semanticType、capability、输出字段必须存在且类型一致。
- 搜索能力必须只读，不得带 SAP 写副作用或审批需求。
- 展示字段必须真实来自返回契约，禁止模型补造规格、城市、名称等。
- 身份键不能为空；同名描述不可用作唯一身份。
- 新增规则纳入 SemanticRelease 的显式源清单及一致性校验。
- 数据版本和语义版本分离；主数据导入不要求每次发布本体。
- 同一 schema/配置变化必须让未完成的旧选择失效，或经显式兼容规则重新验证。

## 5. PostgreSQL 数据模型与主数据导入

### 5.1 数据模型

使用 PG 支持的版本和扩展先检查项目约束，再钉兼容版本。仅在隔离测试环境创建所需扩展；生产安装扩展不在授权内。

最小模型应支持：

- Material、Customer、Supplier 的领域投影，不要求复制全部 SAP 表。
- 来源系统、client、对象类型与编码组成的稳定身份。
- 多语言描述，不把多个语言行当成多个实体。
- 按对象关联的别名，包含来源、适用范围和有效状态。
- 实际需要的区分属性，不构造全企业 EAV 平台。
- 对象与组织范围关系，例如物料工厂扩展；身份与组织可用性分离。
- 数据快照、来源提取时间、加载时间、覆盖范围和有效状态。

编码使用字符串，不丢前导零、不转整数、不套用通用固定长度补零。SAP 内外码转换必须是经核验的对象适配规则。

Supplier/Customer 角色编码不能默认等于 BP 号；没有目标系统依据时保留独立字段与明确边界，不实现猜测转换。

### 5.2 PG 的角色

- SAP 属性为导入投影，不允许通过普通解析 API 改写。
- 本地别名与 SAP 权威字段分开，不能覆盖正式描述。
- 一次用户选中某个候选，只生成当前会话确认，不自动写公共 alias。
- 应用搜索账号只有必要视图的只读权限；迁移/导入使用独立权限。
- 不假定“READ”天然等于“有权读取所有主数据”。

### 5.3 首版导入方式

实现显式的、本地 CSV/JSON 快照导入器，不实现真实 SAP 提取或 CDC。

必须包括：

- 明确列定义、编码、空值、语言和组织关系格式。
- 来源系统/client、数据来源时间、覆盖范围等受验证的批次声明。
- 干跑验证；格式错误或身份重复时不部分发布。
- staging + 原子发布，或等效事务机制，读取不能看到半批数据。
- 失败时继续使用上一有效快照。
- 明确 full snapshot 与 incremental 的语义；本次可仅支持 full snapshot，并对 incremental 明确拒绝。
- full snapshot 只替换声明覆盖范围，不能把未导入的其他系统/对象误删。
- 处理失效/删除，避免已消失对象永久保留为有效候选。
- 导入时间不能冒充 SAP 来源更新时间；来源时间未知时如实记录 unknown。
- 同一快照重复导入应幂等。

提供完全合成的三类对象示例数据，包含重名、不同语言、近似规格、不同组织范围和失效对象。严禁使用仓库中发现的真实客户数据生成公开 fixtures。

### 5.4 本地启动与凭据

提供可复现的本地 PG 启动、迁移、导入与测试说明；可以增加受控 Docker Compose 开发配置，但不得自动安装 Docker、删除卷或改系统服务。

密码、连接串等秘密不得出现在聊天、命令参数、代码、日志或提交中。使用仓库批准的凭据管理/执行器注入方式；示例只写占位符或 credential reference。

离线测试优先隔离容器/本地 socket 等安全测试配置，不能为方便而把真实密码放进 `.env`。缺少安全凭据方式时清楚报告阻塞，不自创明文兜底。

## 6. 检索与消歧策略

### 6.1 检索顺序

在可信可见范围内：

1. 编码精确查找并校验存在性。
2. 正式名称/受治理别名精确匹配。
3. 描述关键词、子串与结构化区分属性检索。
4. PG trigram 召回/排序作为补充，不替代对象身份校验。

不要引入 embedding 作为本次必要依赖。中文描述、两个字短词、英文型号、数字和规格必须有测试；不能宣称 pg_trgm 自动理解中文语义。

保留尺寸、小数点、型号和单位中的业务差异；检索归一化不得把不同规格合并。可维护独立检索文本，但原始值必须保留。

### 6.2 SQL 与性能边界

- SQL 参数化；表/列/排序仅来自白名单可信配置。
- 若语义是字面量子串，正确转义 `%`、`_` 和转义字符，不意外开放任意 LIKE 模式。
- 有界 limit、分页、超时和连接池。
- 极短或没有可用 trigram 的输入，执行有界策略或请求更多信息，不进行无界全库扫描。
- 根据实际查询选 GIN/GiST/B-tree，提供可复现 EXPLAIN/测试；不凭索引存在就宣称性能达标。
- 原始数据库错误不回显 SQL、连接信息或凭据。

### 6.3 选择策略

- 精确编码且当前可见、有效：可以绑定，但必须有验证证据。
- 完整有效覆盖范围内，精确正式名称/受治理别名唯一：可按声明策略绑定，并展示已采用对象；第一版允许采取更保守的确认策略。
- 描述模糊命中，即使只返回一个：请求用户确认。
- 多个候选：显示有用差异并请求选择。
- 过多候选：依据真实可用属性请求一个最有效的补充条件。
- 无匹配：请求补充描述/型号/城市等，不强迫用户必须记得编码。
- 超时、权限不足、数据覆盖不完整、截断或过期：分别表达，不降级成“唯一”或“没有”。

Top-1 不等于唯一；Top-K 只有一条不等于全量范围唯一。响应要区分 complete-result-set 与 partial/truncated，且完整性只在明确的授权范围与数据覆盖范围内成立，不声称企业全局唯一。

同一实体的多语言、别名或组织 join 行应先去重，再决定候选数量。

## 7. 服务端可信实体解析与业务绑定

### 7.1 入口位置

在当前真实业务入口中，目标能力和目标槽位已可确定之后、最终编码绑定和执行之前增加实体解析编排。

不得只接在历史离线分析工具里；不得只加独立搜索页面而让真实聊天路径仍要求用户输入编码。

复核 rule/envelope、READ context v2、HTTP facade 与 in-process DSH 的实际入口。解析所需权限不因缺少 read_state 而失效；不支持路径要明确阻断或声明，不得悄悄走旧路径执行猜测编码。

### 7.2 模型与确定性职责

模型可以产生待验证 mention、目标对象建议和用户选择意图。它不能：

- 自行生成规范编码并直接执行。
- 指定数据库、SQL、bindingId 或可信数据范围。
- 将“我选了第二个”转换成任意编码并自证有效。

实现服务端 `ResolvedEntityRef` 或等价证据，至少绑定实体身份、目标槽位、解析方式、来源/快照、当前 frame/会话和选择状态。

服务端必须校验对象类型与目标输入 semanticType 一致。来源不同、client 不同或同一编码属于不同对象类型时不得串用。

### 7.3 纯 reducer 不做 IO

搜索与 get-by-key 在 IO 编排层执行，产出已验证事件后再交给 reducer。

新增“服务端解析证据”必须有实际验证入口，不能仅在客户端对象中增加 `source=VERIFIED` 就授予可信性。

复用当前的 frame、snapshot、state-version、过期和决策门语义，但不要把实体候选列表冒充 capability 候选列表。

### 7.4 参数绑定

- 根据声明将同一个 Customer 引用绑定到不同能力的 `customer` 或 `customerNumber`。
- Supplier 引用映射为下游实际需要的 `vendor` 等参数。
- 保留本轮已有的 plant/companyCode/date 等无冲突参数。
- 参数校验、注册能力白名单、可见性、CallPlan 与 Gateway 绑定校验继续生效。
- 已有编码形状检查继续作为格式检查，但不能替代实体存在性和权限检查。
- 新输入明确描述另一个对象时，不得静默继承上轮已确认编码。

## 8. 多轮候选选择协议

### 8.1 新增一等实体选择状态

新增 `ENTITY_CHOICE` 或语义等价类型，不滥用 `CAPABILITY_CHOICE`。

候选集保存在服务端 durable store；前端只获取授权展示字段与不透明选择句柄。

至少绑定：

- resolution/candidate-set ID。
- 对象类型、目标槽位、原始 mention 与必要过滤条件。
- 原始候选的稳定身份及展示顺序。
- 当前 principal、conversation/frame、state version。
- registry/semantic 配置版本、Provider、主数据快照。
- 创建与过期时间。

不可仅依赖浏览器回传的完整候选列表，也不可只靠模型记忆维护候选。

### 8.2 用户选择

同时支持按钮与受约束的自然语言：

- “第二个”：绑定原展示顺序，不重新检索后再取第二条。
- “苏州那家”“20 毫米的”：只能在当前候选真实属性中解析；若仍有多个就继续澄清。
- “都不是”：清除当前候选，允许重述。
- 补充描述：建立新的候选集，使旧句柄不能继续选中。
- 改业务目标/对象类型：结束或显式切换旧 pending。

模型解释自然语言时，只能返回候选引用建议；服务端仍验证集合成员、唯一性及当前绑定。

### 8.3 确认前复核

确认时重新验证当前数据版本、实体存在与有效状态、principal/组织可见性。

若快照、规则或权限变化，采用第一版保守策略：旧选择失效并要求重新解析/确认。不可只凭快照不同就静默替换用户选择。

至少覆盖重复点击、并发两个 tab、旧 state version、过期候选、跨会话/跨用户句柄和重放。

继续执行遵守现有幂等/lease 协议；重复提交不能创建多个无关联的恢复执行。不要为了本功能重写原有持久化机制。

### 8.4 前后端一致性

同步修改 Python/TypeScript 类型、序列化、持久化校验、迁移和测试。旧会话缺少新字段时可安全读取；不能迁移的旧 pending 应失效，不能获得新执行权威。

DSH Chat 展示真实候选属性、数据来源/时效提示及继续缩小范围的入口。pending 时不得触发库存、账款等下游业务读取，允许的只是受治理的主数据检索。

## 9. 权限、安全与数据时效

- 主数据搜索本身会泄露商业信息，不能“因为只读”就开放全部记录。
- 可信 principal 和 scope 必须在查询/分页/排序/计数之前落实，不能先取全量再交模型过滤。
- 客户端传入组织参数只能收窄授权范围，不能扩大。
- 当前若只有 placeholder principal，必须明示 sandbox 限制，并实现显式范围约束；不得宣称生产授权已完成。
- 同步作业的提取权限不等于所有聊天用户的查询权限。
- 过期阈值是受控配置，并声明建议默认值未经过生产校准。过期数据不能自动确认；写业务遇到无足够时效证据时必须阻断，不假装已 live 校验。
- get-by-key 查询 PG 只能证明 PG 当前快照状态，不宣称已向 SAP 实时复核。
- 对于本次读取场景，确认候选后若真实 SAP 因对象失效失败，应返回明确失败，不切换到另一个对象继续查。
- 实体选择确认不是 WRITE 审批。既有审批 subject 必须包含最终规范编码；对象改变则旧审批失效。
- 数据库文本、描述与别名均为不可信业务数据，不能作为指令；不得因描述字段包含 Prompt Injection 就调用额外工具或泄露信息。
- 审计记录解析、搜索、候选确认、参数绑定和执行的关联 ID，按仓库现有脱敏规则处理描述、名称与数据范围；不要记录秘密。

## 10. 实施顺序与阶段退出条件

按阶段实施并自检，不把列计划当作完成。

### 阶段 A：契约与 PG 搜索

交付逻辑契约、schema/validator、数据迁移、合成快照导入、真实 PG Provider 与 Gateway 受控 READ 接入。

- 不能依靠 Mock Provider 替代全部 PG 集成测试。

### 阶段 B：Material 端到端

交付待解析 mention、服务端候选集、ENTITY_CHOICE、前端卡片、选择恢复、可信编码绑定。

退出条件：

- 从“不知道编码的描述”开始，在 DSH Chat 同一会话完成选择并恢复库存能力。

- 多候选未确认前不执行库存读取；选中后使用确切编码。
- 无 headless/UI 能力时至少交付自动化协议测试与可复现手工步骤，并明确 UI 未实测，不声称完整 UI 验证。

- 原目标、其他已收集参数和对象类型不串用。

### 阶段 D：回归与交付

退出条件：

- 本功能和受影响的既有测试通过，或逐项准确说明环境阻塞和历史失败。
- SQL 注入、越权、过期/重放、版本漂移和恢复执行有反向测试。
- 文档、运行命令、数据字典、回滚与剩余生产缺口完整。
- HANA 保持明确“未实现”，不存在会返回成功的伪 Adapter。

## 11. 必须覆盖的回归案例

为以下场景建立机器可运行用例；可按当前测试结构组合，不要求每行单独一个文件。

### 检索与数据

1. 描述片段可召回真实合成编码，模型没有生成该编码的权限。
2. 同名不同规格物料产生多个候选。
3. 客户/供应商简称对应多个不同法人。
4. 正式描述、别名、多语言和组织 join 不导致同一实体重复计数。
5. 同一编码在不同 system/client/object type 不混淆。
6. 前导零、字母数字编码、型号、小数规格和特殊字符不丢失。
7. 中文短词与无法有效使用 trigram 的输入执行有界策略。
8. SQL 注入与 LIKE 通配符输入不会改变查询结构或扩大权限。
9. 已失效对象不能被自动绑定；不存在的显式编码被识别。
10. full snapshot 幂等、错误批次不部分发布、不越覆盖范围删除。
11. 数据库不可用/超时不是“无候选”；部分索引覆盖不宣称全局不存在。
12. Top-K 截断不导致唯一性误判。

### 选择与会话

13. “第二个”绑定原候选顺序；查询排序变化不会改变选择。
14. 按城市/规格选择仍歧义时继续询问。
15. 单个模糊候选需确认，不能凭高分自动绑定。
16. 用户“都不是”、补充描述、换对象、换目标能正确清理 pending。
17. 新描述不能被旧 confirmed slot 吞掉。
18. 旧候选、过期候选、跨用户/会话选择、伪造 ID 被拒绝。
19. schema/语义版本、PG 快照、权限变化使旧选择安全失效。
20. 重复点击、并发 continuation 和 stale state version 不错绑对象。
21. 选择后保留原目标与 plant/date 等参数，恢复执行一次受治理流程。
22. 模型捏造 canonical code、source 或 candidate-set 成员均不获执行权威。
23. 多个未解析槽位时逐个完成并保存绑定，不把所有候选做笛卡尔组合。

### 集成与安全

24. Material、Customer、Supplier 根据声明走同一机制。
25. 不同客户槽位名映射正确，不因变量名不同重写 resolver。
26. 未完成实体确认时下游业务能力不执行。
27. 确认实体不产生 WRITE ApprovalRecord；既有写审批不被绕过。
28. 无 PG 配置/feature flag 关闭时，旧编码路径行为按声明保持，不偷偷猜码降级。
29. 旧会话迁移不获得额外执行权威。
30. 描述内的恶意指令作为普通数据展示，不改变工具调用与权限。

新增 fixtures 只能使用合成数据。LLM-as-judge 不能单独验收权限、身份绑定、SQL 或审批安全。
