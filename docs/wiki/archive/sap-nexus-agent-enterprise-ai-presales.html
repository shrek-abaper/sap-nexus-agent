SAP Nexus Agent

从 SAP 事务调用，升级为企业级可治理 AI 能力本体。

SAP Nexus Agent 不是把 LLM 接到 SAP 上，而是为企业核心系统建立一层 AI-era control plane：大模型负责理解和推理，Harness 负责能力闭集、参数校验、受控执行、证据事实、人审写入和审计回放。

The Enterprise AI Gap

普通 Agent 可以赢得 Demo，却很难赢得生产系统的信任。

企业真正的 AI 难题不是“模型会不会回答”，而是“模型能不能被允许进入核心流程”。在 SAP、ERP、供应链和财务系统里，安全、权限、证据、审批和审计不是附加项，而是进入生产的门票。

!

LLM 自由选工具

工具列表越多，误选、幻觉、越权和参数猜测风险越高。企业核心系统不能依赖 prompt 运气。

!

API 缺少业务语义

BAPI、RFC、OData、REST endpoint 只是技术入口，不等于受治理的业务能力。

!

执行后才补日志

如果没有 CallPlan、证据链和 trace，审计、追责、回放和合规都很难成立。

!

写入动作不可控

SAP 写入必须绑定人工审批、影响说明、执行结果和失败原因，不能交给模型直接决定。

Customer Conversation Path

三句话讲清楚：为什么是现在，为什么是 SAP Nexus，为什么可以安全部署。

客户现场不需要先听一堆技术名词。最佳售前路径是先建立时代判断，再给出差异化架构，最后回答生产系统最敏感的问题：是否可控、可证据化、可审计。

Why now

AI 把自然语言变成企业入口。

大模型让业务人员可以直接表达目标，但企业系统仍然运行在权限、流程、数据和审计约束之内。新的机会不是“聊天”，而是重构业务意图到系统能力的连接方式。

Pitch line: Natural language becomes the new front door; governance remains the enterprise backbone.
Why SAP Nexus

我们建模能力，而不是暴露工具。

SAP Nexus Agent 将 SAP 和周边系统能力沉淀为 Capability Ontology：每个能力都有语义、输入输出、治理、副作用、证据、执行绑定和评测链接。

Pitch line: APIs expose systems; capabilities expose governed business intent.
Why safe

LLM 不执行，Harness 才执行。

模型只在闭集能力中理解、排序和解释。真正的执行必须经过 MatchDecision、CallPlan、Gateway validate、ExecutionResult、ReasoningFact、人审和审计回放。

Pitch line: The model reasons; the deterministic harness governs execution.
From API Catalog To Capability Ontology

能力不是接口，而是企业 AI 时代的复用资产。

API 暴露系统，Capability 暴露受治理的业务意图。SAP Nexus Agent 将企业操作建模为带语义、治理、证据、执行绑定和评测链接的能力本体，让 AI 面向业务目标推理，而不是面向技术接口猜测。

Yesterday

API catalog exposes systems.

  • 面向技术接口组织，业务意图需要人或 prompt 临时解释。
  • 参数、权限、副作用、证据和审批分散在不同系统。
  • LLM 面对的是工具名称，而不是企业能力模型。
SAP Nexus Direction

Capability ontology exposes governed intent.

  • 每个能力都有稳定 `capabilityId`、业务对象和语义输入输出。
  • 治理属性、审批规则、证据字段和执行绑定在 Registry 中显式声明。
  • AI 只在闭集能力中推理，Harness 负责最终校验和执行边界。
Capability as a Product

把企业能力沉淀为可治理、可评测、可演进的本体节点。

一个 SAP 能力不再只是 `rfcName` 或 endpoint，而是一个包含业务语义、输入输出、治理约束、证据映射、执行绑定和审计策略的企业资产。

Semantics

业务语义

能力绑定业务对象、字段含义和输入输出语义，而不是只暴露技术参数。

Governance

治理规则

副作用、审批、权限、状态和风险等级在执行前确定性校验。

Evidence

证据优先

每个结论必须来自结构化事实，Narrative 只能引用已有 ReasoningFact。

Binding

执行绑定

技术执行细节留在 allowlisted binding catalog，用户和 LLM 不能覆盖。

Evaluation

评测链接

能力变更触发匹配、参数、执行、证据和叙事回归评测。

Evolution

可迁移演进

YAML Registry 可逐步迁移到 OWL、SHACL 或 Graph Registry，不推倒重来。

Harness Engineering

LLM 不是生产系统操作员，而是受治理的推理协作者。

SAP Nexus Agent 的主架构不是 ReAct-first，也不是裸 tool-calling。所有可执行动作都必须先变成注册能力、可校验计划、受控 Gateway 调用、结构化事实和可回放 trace。

L1

User Intent

自然语言业务目标、上下文、澄清输入。

L2

Intent Harness

能力匹配、参数抽取、MatchDecision。

L3

Capability Registry

能力本体、治理属性、执行绑定。

L4

CallPlan

执行前可审查、可验证、可回放的计划。

L5

Gateway Family

JCo / OData / CDS / REST JSON 受控执行。

L6

ExecutionResult

SAP 或外部系统返回的标准化结果。

L7

ReasoningFact

用于推理和叙事的证据化事实。

L8

Recommendation

基于事实和规则生成建议，不直接写入。

HITL

Human Approval

写入动作必须经人审确认。

AUDIT

Replay

按 traceId 回放完整链路。

Enterprise-safe principle: LLM output is advisory until accepted by deterministic Harness. 外部只能传入 `capabilityId`，不能传入裸 `rfcName`、endpoint、headers、token 或 payload mapping。
Scaling To Thousands Of Capabilities

海量能力时代，匹配必须成为可审计决策流水线。

当能力从几十个扩展到上千个，不能让 LLM 直接看全量工具列表。SAP Nexus Agent 采用混合式匹配：规则守住安全边界，Registry / Index 做候选召回，LLM 只在小候选集合中排序和解释，Harness 输出最终 MatchDecision。

01Intent Normalization归一 intentType、业务对象和参数草稿。
02Domain Routing缩小到 MM、PP、SD 或 Action domain。
03Candidate Retrieval基于 keyword、example、embedding、input/output 召回。
04Governance Filter权限、副作用、审批、状态、binding readiness 硬过滤。
05Candidate RerankLLM 只在 top-N 候选内排序和解释。
06Parameter Fit缺参澄清，歧义不猜，非法参数拒绝。
07MatchDecision进入 CallPlan、澄清、拒绝或 planner。

Enterprise Value

企业级 AI 的价值，不是多一个助手，而是多一层可信操作系统。

对 CIO 和架构负责人而言，SAP Nexus Agent 的价值不是“让 AI 回答问题”，而是建立一层可控、可审计、可扩展的企业能力操作层，连接业务意图与核心系统执行。

01

Governed AI

AI 可以理解意图，但不能绕过 Registry、schema、权限、副作用和审批边界。

02

SAP-safe Execution

不暴露裸 RFC、OData URL、CDS path、REST endpoint 或 payload mapping。

03

Evidence-first Reasoning

每个业务结论都必须引用结构化事实，避免无证据叙事和模型幻觉。

04

Human-approved Action

写入动作必须绑定建议版本、审批记录、执行结果和 SAP RETURN。

05

Replayable Audit

从 intent 到 Gateway 到事实到审批，每一步都可按 traceId 回放。

06

Capability Reuse

能力沉淀为企业资产，可跨场景、跨系统、跨团队复用和治理。

Pre-sales Story

从一个库存问题，走向受控采购建议。

售前演示不应只展示一次工具调用，而要展示企业级 AI 如何识别目标、补齐事实、形成证据化推理，并在写入前进入人工审批。

“
A100 下周生产够不够？如果不够，给我一个采购建议。

这不是一个简单库存查询。它需要库存、需求、在途、采购提前期、安全库存和业务规则共同支撑。

01

匹配能力，而不是猜工具

系统先识别为缺货风险判断，库存能力只是候选事实来源之一。

02

升级到 Planner

目标需要多个 facts，输出 `ESCALATE_TO_PLANNER`，而不是强行执行单能力。

03

组合 Read Capabilities

读取库存、需求、open PO、lead time 等事实，统一为 ReasoningFact。

04

生成证据化建议

RecommendationPlan 引用 facts 和 rules，说明缺口、原因和建议数量。

05

写入前人审

如需创建 PR，进入 Human Approval；未审批不写 SAP。

Roadmap To Enterprise Capability OS

从第一条 Read Function，演进到企业能力 AI 操作层。

SAP Nexus Agent 采用纵切优先、边界先行的路线：先证明 read-only 事实链路，再扩展匹配、推理、建议、人审写入和图谱治理。

Read Function

受控库存可用量查询，形成 ExecutionResult 和 trace。

Capability Registry

多能力、schema、governance、executor binding。

Capability Matching

混合式召回、过滤、rerank、MatchDecision。

Reasoning

基于 facts 的缺货风险、补货建议和解释。

Human-approved Action

审批后创建 PR draft 或提交受控业务动作。

Graph Governance

迁移到 OWL / Graph Registry，支持跨域能力治理。

Closing Vision

Not another SAP chatbot. The governed operating layer for enterprise AI execution.

SAP Nexus Agent 将自然语言、能力本体、SAP 执行、证据推理、人工审批和审计回放连接为一个可量产的企业 AI 控制面。它让企业把大模型带进核心业务流程，同时保留生产系统必须具备的治理、边界和信任。
