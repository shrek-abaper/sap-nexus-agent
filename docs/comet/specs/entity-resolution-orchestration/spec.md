# 服务端实体解析编排与参数绑定

## 入口

在当前真实业务入口（DSH Chat 服务端链路）中，目标能力与目标槽位已确定之后、最终编码绑定与执行之前插入实体解析编排。

不只接在历史离线分析工具（ontology_planning fixtures 路径）；不只加独立搜索页面而让真实聊天路径仍要求用户输入编码。不支持的路径明确阻断或声明，不悄悄走旧路径执行猜测编码。

## 模型与确定性职责

模型可产生待验证 mention、目标对象建议、用户选择意图。模型不能：自行生成规范编码并直接执行；指定数据库、SQL、bindingId 或可信数据范围；把"我选了第二个"转换成任意编码并自证有效。

服务端 `ResolvedEntityRef`（或等价证据）至少绑定：实体身份、目标槽位、解析方式、来源/快照、当前 frame/会话、选择状态。新增"服务端解析证据"必须有实际验证入口，不能仅在客户端对象上加 `source=VERIFIED` 就授予可信性。

服务端校验对象类型与目标输入 semanticType 一致；来源不同、client 不同或同一编码属不同对象类型时不得串用。

## 纯 reducer 不做 IO

搜索与 get-by-key 在 IO 编排层执行，产出已验证事件后交给 reducer。`reduce_context()` 保持无 IO、无数据库查询、无模型调用。

复用现有 frame、snapshot、state-version、过期与决策门语义；实体候选列表不冒充 capability 候选列表。

## 参数绑定

按声明把同一 Customer 引用绑定到不同能力的 `customer` 或 `customerNumber`；Supplier 引用映射为 `vendor` 等下游实际参数。

保留本轮已有的 plant/companyCode/date 等无冲突参数。参数校验、注册能力白名单、可见性、CallPlan 与 Gateway 绑定校验继续生效。

已有编码形状检查继续作为格式检查，但不替代实体存在性与权限检查。新输入明确描述另一个对象时，不得静默继承上轮已确认编码。

## 恢复执行

确认编码后恢复原目标能力执行，遵守现有幂等/lease 协议；重复提交不创建多个无关联恢复执行。不重写原有持久化机制。

多候选未确认前不触发库存、账款等下游业务读取；pending 时允许的只是受治理的主数据检索。

确认候选后若真实 SAP 因对象失效失败，返回明确失败，不切换到另一个对象继续查。
